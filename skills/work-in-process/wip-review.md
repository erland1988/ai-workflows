# wip-review

编码后全面复核，**循环执行**：对照实际产物检查一致性 → 发现问题先修正文档 → 再修改代码 → 重新验证 → 直到三者（design / plan / 源码）完全一致。

> ⚠️ **wip-review 不输出独立报告文件。** 一致性确认后更新 `ledger.md` 即可。审查记录由 ledger 详细日志承载，不额外产出 `review.md`。

## 核心原则：先修文档，后修代码

发现问题时优先修正 design/plan 文档使其与意图对齐，再直接修正代码使其与源码对齐。循环直到三者一致。文档是真相源，代码是实现。

## 执行流程

### 第一轮：对照检查

按以下维度逐一检查，记录不一致之处：

1. **design.md ↔ 源码**
   - 数据库概览中的表清单，其 DDL 是否在各模块中完整落地？
   - 变更文件汇总与 `git diff` 实际改动是否一致？
   - 模块划分与实际目录结构是否吻合？

2. **plan.md ↔ 源码**
   - 每个 Step 的「文件/位置/操作」是否已正确实现？
   - 有无 plan 中定义但遗漏的步骤？
   - 有无 plan 未定义的额外改动？

3. **plan.md ↔ design.md**
   - plan 的变更文件与 design 的变更文件汇总是否一致？
   - plan 的 Phase 划分是否覆盖 design 的所有模块？

4. **编译与测试**
   - 编译是否通过？
   - 测试矩阵是否逐项验证？回归测试全绿？

5. **Git 检查**
   - `git status` / `git diff` 核对实际改动范围
   - 确认未触及计划外文件（如有则需说明或还原）

### 轮次循环

1. 输出本轮检查结果（口头汇报，列出不一致项）
2. 按「先修文档，后修代码」原则逐一修正
   - 文档不一致 → 直接修 design / plan
   - 代码不一致 → 主会话直接修正代码（子代理只参与 wip-code 的 worktree 编码，不在此阶段介入）
3. 修正完成后重新验证
4. 循环直到 0 不一致
5. 更新 `ledger.md`，标记审查完成

**wip-review 阶段修正代码由主会话直接执行**（子代理只在 wip-code 的 worktree 内参与编码，此阶段代码已合并到基分支、worktree 已清理）：
- **修正依据**：本轮不一致项直接作为修正目标，无需生成文件
- **当前代码**：基于主工作区（代码已合并到基分支）
- **Git 状态**：用 `git log --oneline -5` 定位合并提交范围

### 输出格式（口头）

```
📋 wip-review 检查结果

✅ 一致项:
   - design.md ↔ 源码：数据库概览中的表全部落地
   - plan.md ↔ design.md：变更文件一致

❌ 不一致项:
   - plan.md Step 3（startNextPlan 缩进）→ 文档领先于代码，主会话直接修正

🔄 第 2 轮检查后: 0 项不一致

✅ 审查通过
```

## 与 implementer 子代理的关系

| | implementer 子代理 | wip-review |
|---|---|---|
| 时机 | wip-code 中每个模块编码时 | 全部编码完成后 |
| 载体 | 子代理在独立 worktree 内 | 主会话在主工作区 |
| 粒度 | 模块级自审查（实现后自检自修） | 整体（design / plan / 源码 三者一致性） |
| 视角 | 单代理自查（换审查员视角） | 主会话独立终态校验 |
| 输出 | 返回状态/提交/测试/遗留，记入 ledger | 更新 ledger.md，标记审查完成 |

两层互补：implementer 在编码时做模块级自检，wip-review 做终态整体一致性校验——单代理自审查的独立性局限，由 wip-review 兜底。

## 依赖

无外部脚本依赖。全部检查由 AI 直接执行。
