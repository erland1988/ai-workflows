# wip-build

生成设计文档（总体设计 + 模块设计）和执行计划（Phase/Step 结构），**自动判断模块数量**并根据职责**自动命名**。

> ⚠️ **只产出设计文档和计划，禁止修改任何项目源码。** 编码只在 `wip-code` 阶段执行。

## 两阶段产出

wip-build 分两步完成：

```
阶段 A: 生成设计文档（总体 design.md + 模块 design.md）
阶段 B: 为每个模块生成执行计划（plan.md）
```

两阶段**在一次 wip-build 调用中连续完成**，中间无需用户介入。

---

## 阶段 A：生成设计文档

### 执行流程

1. 读取当前项目代码结构，理解技术栈、命名风格
2. 与用户对话澄清需求（背景、范围、约束）
3. **自动判断模块数量**：
   - **简单需求**（单功能/单文件/单一逻辑）：单模块，自动命名（如 `core`, `validator`, `service`）
   - **复杂需求**（多独立子系统/多层架构）：自动拆分多个模块

   > **core 骨架去留**：wip-init 预建的 `modules/core` 骨架——简单需求沿用；拆分为多模块时，core 若被更细模块替代则重命名/删除，**不残留无用模块**。
4. **智能模块命名**（根据职责）：
   | 模块职责 | 自动命名示例 |
   |---------|-------------|
   | 数据模型定义 | `data-models` |
   | 数据库迁移 | `db-migrations` |
   | 业务逻辑实现 | `business-logic` |
   | API 接口层 | `api-endpoints` |
   | 权限校验 | `auth-validation` |
   | 缓存优化 | `cache-optimization` |
5. 生成分层设计文档：
   - **总体设计** → `.wip/{name}/design.md`
   - **模块设计** → `.wip/{name}/modules/{module}/design.md`

### 设计文档编写原则

**设计方案**面向临时评审，写一份总体设计概述：

- **总体思路**：用 3-4 句话讲清楚"要解决什么问题 → 用什么方式解决 → 核心设计原则"。
- **架构概要**：说明改动涉及的系统层次（数据层/业务层/接口层）、各层职责划分、模块间调用关系，标注上下游依赖及是否向后兼容。
- **数据库概览**：表清单（表名 / 用途 / 所属模块 / 关键字段），不写完整 DDL。每张表的完整 DDL 见对应模块设计。
- **关键决策**：用表格列出 2-5 个关键设计取舍（如：为何选择该方案而非其他、状态机流转设计依据），每项包含方案/理由/风险。

**需求背景**写明：触发条件、范围边界、前置校验、状态约束、幂等语义。从对话中提取所有需求要点。

**变更文件汇总**作为独立章节，表格列出每个文件的操作类型（新增/修改/删除）及对应执行步骤，作为回溯速查表。

**构建顺序**用依赖图标注阶段间推进顺序及阶段内并行链路，点明关键步骤的前置依赖。

### 总体设计文档结构

- **参考资料**：业务流程图、数据表关系、关键方法签名
- **需求背景**：触发条件、范围边界、前置校验、状态约束、幂等语义
- **设计方案**：总体思路（3-4句）、架构概要（系统层次/职责划分/调用关系）、**数据库概览（表清单）**、关键决策表（方案/理由/风险）
- **模块划分**：表格（模块/说明/前置依赖）
- **变更文件汇总**：表格（文件/操作/所属模块）
- **依赖关系图**：模块间依赖顺序

### 模块设计文档结构

- **模块边界**：职责、不做的事、接口契约（输入/输出/错误处理）
- **数据模型**：新增或修改的实体、字段、类型
- **状态机**（如有）：状态流转图
- **实现思路**：技术选型、关键算法、设计模式
- **预估变更**：表格（文件/操作/说明）
- **依赖**：前置模块、后置模块

## 阶段 B：生成执行计划

设计文档完成后，为每个模块生成 `plan.md`（`.wip/{project}/modules/{module}/plan.md`）。

### 执行流程

1. 读取模块设计文档 `.wip/{project}/modules/{module}/design.md`（阶段 A 产出）
2. **按层次分阶段拆解**（Phase 按项目实际分层裁剪，某层不存在则跳过）：
   - Phase 1: 数据层（DDL/SQL/迁移脚本）
   - Phase 2: 模型/实体（数据结构定义）
   - Phase 3: 业务逻辑（核心业务实现）
   - Phase 4: 接口/入口（API/CLI/UI）
   - Phase 5: 联调验证（集成测试）

   > **裁剪规则**：无数据库层（纯前端/脚本/配置项目）跳过数据层 Phase；单层项目可合并 Phase。原则是**只保留实际存在的层**，且每个 Phase 用一句话说明「为什么存在」。联调验证阶段始终保留。
3. 每阶段拆分为**可执行步骤**（2-5分钟/步骤）
4. **步骤统一模板**（每个步骤缺一不可）：
   - **文件**：目标文件路径，标注新建/修改
   - **位置**：精确到方法名 + 行号锚点
   - **背景**：为何改（仅在原因不直观时需要）
   - **操作**：具体代码/SQL，可直接落地
   - **验证**：编译/单测/联调的具体方式
5. **联调验证阶段**用测试矩阵呈现：`# | 场景 | 前置条件 | 操作步骤 | 预期结果`，覆盖正常流、边界、幂等、并发
6. 输出执行计划 → `.wip/{project}/modules/{module}/plan.md`

### 核心产出要求

1. **按层次分阶段**：数据层 → 模型/实体 → 业务逻辑 → 接口/入口 → 联调验证（按项目实际裁剪）
2. **步骤统一模板**：`文件` / `位置` / `背景` / `操作` / `验证`
3. **测试矩阵**：`场景 | 前置条件 | 操作步骤 | 预期结果`
4. **步骤号管理**：一经分配不复用；取消步骤保留占位
5. **依赖接口契约**：模块 plan.md 开头列出前置模块暴露的关键签名 / DDL / 类型，供实现者对接（无前置模块则注明「无」）
6. **模块风险标注**：模块 design.md 标注 `低风险` / `高风险`（高风险 = 核心逻辑 / 数据迁移 / 多文件协调），供 wip-code 判断执行模式

### 步骤号管理规则

- 步骤号一经分配不复用
- 迭代中被取消的步骤保留占位，注明「已移除 + 原因」
- 不静默删除，保持可追溯

## Ledger 更新

全部完成后 **自动更新 ledger.md**：
- 标记各模块 `设计` + `计划` 为 ✅
- 在决策记录中追加模块划分、关键设计取舍、阶段划分和步骤拆分理由

## 依赖

无外部脚本依赖。模块命名由 AI 根据职责直接推断，无需 Python 脚本辅助。
