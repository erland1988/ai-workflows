# Worklog

把一个 git 分支的提交历史 + 设计文档，归纳成**业务视角**的工作进展，落到需求表 / 周报。

**核心判断**：commit message 说的是「改了什么代码」，需求表要的是「做了什么功能」。中间的翻译靠**设计文档**，不靠 commit message —— 只读 commit 写出来的进展一定是代码视角的。

## 输入

| 项 | 必需 | 默认 |
|---|---|---|
| 仓库路径 | 是 | — |
| 分支 | 否 | 当前分支 |
| 基线 | 否 | `main`，可指定 `dev` |
| 目标表格 / 行 | 否 | 先输出草稿，由用户指认 |
| 周区间 | 否 | 按提交日期自动归周 |

## 执行步骤

### 1. 定位分支增量

```bash
git -C <repo> branch --show-current

# 分叉点（增量分析的起点）
git -C <repo> log --oneline -1 $(git -C <repo> merge-base <base> <branch>)

# 增量提交 —— 这才是分析范围
git -C <repo> log --oneline --pretty="%h | %ad | %s" --date=short <base>..<branch>

# 反向：基线有而分支没有的（合并前需注意）
git -C <repo> rev-list --count <branch>..<base>

# 未推送的提交
git -C <repo> log --oneline @{u}..<branch>

# 工作区是否干净
git -C <repo> status --short
```

**先确认分叉点，再看增量**。别直接 `git log -30` —— 那样会把已经合进基线的历史一起算进来，进展会重复计入。

### 2. 看改动范围

```bash
git -C <repo> -c core.quotepath=false log --name-only --pretty="%n===== %h %s =====" <base>..<branch>
git -C <repo> -c core.quotepath=false log --stat --pretty="%n===== %h %s =====" <base>..<branch>
```

`-c core.quotepath=false` 让中文文件名正常显示，否则是八进制转义。

### 3. 找设计文档（关键一步）

按优先级扫这些目录：

```
docs/wip/   docs/design/   .wip/   docs/
```

设计文档是**业务语义的最佳来源**，通常含 `需求背景 / 范围边界 / 设计方案 / 关键决策`，信息密度比 commit message 高一个量级。文件名常带日期前缀（`20261014_xxx.md`），可直接用于归周。

- 文档数 ≤ 5：直接读「需求背景」段（通常在前 60 行）
- 文档数 > 5：用 subagent 并行摘要，避免塞满上下文。摘要要求聚焦业务、不罗列代码行号和文件路径

### 4. 归纳主题

- **按主题聚类，不按 commit 罗列**。十几条提交往往只对应 3~4 个主题
- **过滤流程噪音**：`chore(comate): archive`、`record verify passed`、`docs: add verify report`、`docs: 归档...`、`Merge branch` —— 这些是流程产物，不写进进展。但**设计文档归档提交要读**，只是不单独成条
- **识别遗留链**：设计文档里的「前置项目 / 后续项目 / 遗留项 / 待办」往往比本次改动更能说明进展。典型：某轮用占位实现、下一轮替换成真值
- **标记反复**：做了又回退、口径切换、方案推翻 —— 这些体现真实工作量，要保留

### 5. 按周切分

按提交日期归入自然周（周一~周日）。每行需求一周一列。

⚠️ 表格的周列**通常插在最左**，旧的往右推，不是往后追加。

### 6. 生成三列文案

见下节规范。

### 7. 先出草稿，确认后写入

**不直接写表格。** 表格是协作共享的，先输出对照草稿：

```
行号 ← 需求名 ← 归到的提交 ← 建议文案
```

用户确认后再写。存疑的行（状态与分支现状矛盾、归属不确定）**单独列出并提问**，不要自行判断后写进去。

## 三列写法规范

### 任务

一行一条**可独立验收的需求项**，不是模块名。

- 格式：`【YYYYMMDD】需求简述`，日期取需求提出 / 排期日
- ✅ `【20261008】用户记忆接入小红书数据源`
- ❌ `租赁监管平台` —— 项目名，与「项目」列重复
- ❌ `业务数据处理` —— 太笼统，无法验收

### 描述

回答「这是什么」，说清**范围与边界**。

- 动词开头，一两句话
- ✅ `企业端支持高校管理项目、房源、合同` —— 对象 + 动作 + 范围
- ❌ `…开发完成，现在为假数据阶段还未接入真实数据` —— 后半句是进度，该挪到周进展列

### 周工作进展

**先读表头** —— 口径通常写在表头里（如 `(本周工作--进度+风险/下周计划）`）。

三档粒度，同一列内保持一致：

| 场景 | 写法 |
|---|---|
| 正常推进 | `已完成` / `已上线` |
| 有补充 | `状态，补充说明`（如 `已上线，正在验收`） |
| 有风险 / 跨周 | `进度：…` + `下一步计划：…` + `难点：…` |

- **空 ≠ 无进展**。没进展就明写 `本周无进展，等待PRD`，读者才分得清「没做」和「没填」
- **状态词统一**：`调研中 → 需求中(MRD/PRD) → 已排期 → 开发中 → 已转测 → 已完成 → 已上线`，不要 `已完成` / `已经上线` / `完成` 混用
- **分支 / 版本信息**：老表常有「备注」列专放分支名（如 `feature/group-city-filter`）；新表若没有这一列，要么并进进展（`已上线（chat-ws-v8.26.10）`），要么告知用户补一列

## 读取既有表格的注意点

- **表结构会随版本改版**。同一个列名在不同时期的含义可能相反（老表的「任务」是模块、新表的「任务」是需求）—— **先读表头确认口径，不要沿用旧列的写法**
- 先取子表清单（`+workbook-info`）再按子表名读，不要猜 `Sheet1`
- 行号一律从 `[row=N]` 前缀读，不要用「序号」列推导（可能跳号）
- 只读问答可忽略"数据没读全"警告；涉及写入必须先覆盖完整区域

## 红线

- **git 操作只读**：`log` / `show` / `diff` / `status` / `branch`。禁止 `add` / `commit` / `push` / `merge` / `rebase` / `checkout`
- **不编造**：提交与设计文档里没有的信息不写。没有来源就留空，并在交付说明里逐项列出缺什么
- **归属存疑先问**：如状态标「已上线」但分支未合并到基线，先向用户核实，不要自行判定
- **写入前必须确认**：表格改动对外可见，先出草稿
