# GitWorklog

从 git 分支反推**业务视角的工作进展**，用于补充需求表 / 周报。

## 解决什么问题

需求表里要填「这条需求本周做到哪了」，但工作痕迹只存在于代码仓库里。直接看 commit 写不出可读的进展 —— `fix(job): normalize round POI distance unit` 对应的是业务上的「交通配套数据格式修正」，中间这层翻译没人做。

本技能把这条链路自动化：**分支增量 → 设计文档 → 主题归纳 → 三列文案**。

## 快速开始

```
分析下 D:\www\php7\rental-supervision-platform-agent 的 feature/university 分支，帮我补需求表
```

技能会自动定位分叉点、拉增量提交、扫 `docs/wip/` 下的设计文档，最后输出草稿供你确认。

## 流程

```
确认分支与基线 (merge-base)
    ↓
拉增量提交 <base>..<branch>        ← 不是 git log -30，避免把已合并的历史重复计入
    ↓
扫设计文档 docs/wip/ .wip/ docs/design/
    ↓                              ← 业务语义的主要来源
按主题聚类 + 过滤流程噪音
    ↓
按提交日期归周
    ↓
生成三列文案（任务 / 描述 / 周工作进展）
    ↓
输出草稿 → 用户确认 → 写入表格
```

## 三列口径

| 列 | 回答什么 | 关键约束 |
|---|---|---|
| 任务 | 这是哪条需求 | 一行一条可验收项，`【YYYYMMDD】简述` |
| 描述 | 这条需求做什么 | 说清范围与边界，**不写进度** |
| 周工作进展 | 本周做到哪了 | 进度 + 风险 / 下周计划，口径以**表头**为准 |

## 几个容易踩的坑

**先确认分叉点再看增量**。直接 `git log -30` 会把已经合进基线的历史算进来，进展重复计入。

**commit message 不是进展来源**。它是代码视角的，且混着大量流程噪音（`chore(comate): archive`、`docs: add verify report`）。真正的业务语义在设计文档里。

**设计文档里的「遗留项」比本次改动更值钱**。比如某轮用 `rand(1,10)` 占位、下一轮才换成真值 —— 只看第二轮会觉得「就改了几行」，看遗留链才知道这是三步走的收尾。

**表结构会改版**。同一个列名在不同时期含义可能相反（老表的「任务」是模块名、新表的「任务」是需求名）。改版后沿用旧列写法会整体错位，先读表头。

**空着 ≠ 没进展**。没进展明写「本周无进展，等待PRD」，读者才分得清是没做还是没填。

## 红线

- git 操作**只读**，不改仓库状态
- 提交与设计文档里没有的信息**不写**，没来源就留空并说明
- 表格改动对外可见，**先出草稿再写**
